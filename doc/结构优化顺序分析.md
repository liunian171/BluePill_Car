## 0. 核心结论

**从上层开始，但把改动分成两类，顺序不同：**

- **接口 / 契约类改动**（改签名、改依赖方式）→ **先做，自下而上**
- **实现 / 搬迁类改动**（搬代码、收编逻辑）→ **后做，自上而下**

一句话原则：**先定契约，再搬实现**。上层组件必须建在最终接口上，否则接口一变、上层返工两次。

---

## 1. 为什么整体从上层开始

|  #  | 理由     | 说明                                                                      |
| :-: | ------ | ----------------------------------------------------------------------- |
|  1  | 依赖传播方向 | 改上层 = "消费"下层，编译器立即兜底；改下层 = 级联到所有上层调用点，破坏面大                              |
|  2  | 痛点位置   | 高严重度 2 项中 C1 纯上层；C2 的收益（可 PC 测试）服务于上层巡线融合；main.c 本身就是耦合热点               |
|  3  | 下层已经健康 | pwm/uart/gpio/encoder 五套 ops 驱动是全库质量最好的部分，且已实车验证——动它要重新走硬件在环回归，成本最高收益最小 |
|  4  | 回归手段   | 上层改动可用"编译 + 串口命令回归 + PC 测试桩"闭环验证；下层改动只能上实车                              |

> 直觉上"底层是地基所以先改底层"在本项目不成立：地基没裂，裂的是地基上面的施工层。

## 2. 两类改动的划分与顺序

| 类别     | 典型项                                                                            | 特征                  |  顺序 |
| ------ | ------------------------------------------------------------------------------ | ------------------- | :-: |
| 接口/契约类 | C2 传感器注入（line_follower 加读取接口）、C5 OLED 句柄注入（init 加 I2C_Handle 参数）、C7 init 加方向参数 | 改的是"调用约定"，上层绑定点要跟着动 |  先  |
| 实现/搬迁类 | C1 收编协议分发、C3 抽 steering / speed_loop 组件、C4 仲裁机制、main.c 减肥                      | 不改下层接口，只动实现位置       |  后  |

关键事实：C2/C5 这类接口改动**只影响 main.c 的接线行（init 调用），不影响业务逻辑**。先做它们，后续上层搬迁只改几行绑定代码，返工成本极低。

## 4. 判断口诀（可复用的决策框架）

以后每次纠结先后，问两个问题：

1. **这个改动会不会改下层接口？** 会 → 属于"契约"，排在使用它的上层重构**之前**
2. **改完怎么验证？** 只能上实车 → 尽量少动、攒批验证；能 PC/串口回归 → 可以大胆先动

## 5. 风险提醒

C2 动的是 line_follower（巡线唯一权威模块）：改完必须先用现有文本命令（L 1 / GK / GS）在台架回归，再上实车；**不与 C1/C3 改动混在同一次烧录里**——一次烧录只验证一件事。

## 9. C 轨道三点详解（2026-09-11）

> "C 轨道"= 架构收口三项。三者共用同一个改造模板（契约先行 / 纯逻辑组件 / 注入 + tick 外部化 / PC 桩），是"把已跑通的逻辑搬进正确的层"的主力。

### 9.1 C1 桥接层家族契约（解决 S5/S6/S8/S11 + 评审 C5/C7）

| 项 | 内容 |
|----|------|
| **现状问题** | 四个桥各写各的：`motor_bridge` init 无 id 检查；`servo_bridge` 有 id 检查但无 handle 校验且无错误通道；`imu_bridge` 是"胖桥"（含 ~90 行校准管线）+ 堆 `new`；`oled_bridge` 是无 id 单例。错误通道形态完全没定（非法输入统一静默 `return`，违反指南义务 6） |
| **契约要定的 5 件事** | ① **init 签名统一**（`id` + 配置结构体 + `void* handle`，还是别的形态）② **错误通道形态**（返回码 vs 错误日志 vs 两者，二选一并全局一致）③ **id 容量与静态池模板化**（同一套 `pool + placement new` 样板，配越界检查）④ **oled 无 id 单例归一**（显式 `id=0` 还是保持无参）⑤ **硬件差异上提**（评审 C7：`M1 方向取反` 这类布线差异改为 init 参数，桥层回归纯转发） |
| **为什么排在最前** | 它是**契约类改动**——后面的"实现搬迁"（速度环、姿态、C1 命令链收编）都要建在它之上；不先定，新写的桥接代码会各自长一套 |
| **验收标准** | 四桥签名一致；非法输入走同一错误通道（无静默 return）；每桥 id 越界 + handle 空指针均被拦；`imu_bridge` 不再含校准逻辑且无堆 `new` |
| **风险** | 中。签名一变，四处调用点（含 main.c 与 imu_bridge）都要跟改；建议一次只改一个桥并台架回归 |

### 9.2 C2 速度环组件抽取（评审 C3，执行栈另一半）

| 项 | 内容 |
|----|------|
| **现状问题** | PID 速度环 + 前馈 + 编码器解卷绕（约 50 行）锁死在 `main.c` 的 50ms 块；`kp/ki/kd`、前馈系数 `0.3`、解卷绕阈值 `30000/65536`、`max_rpm` 全是 main.c 里的字面量（评审 §3.3 标定散落） |
| **目标形态** | `speed_loop` 执行组件（与 `steering` 同构）：`speed_loop_update(now, target[2], dir[2], enc[2])` → 内部 PID + 前馈 + 解卷绕 → 经**注入的输出函数**写 `motor_bridge`。纯 C、零 HAL、tick 由调用方传入 |
| **与 steering 的对称性** | `steering` 管"意图 → 舵机角"，`speed_loop` 管"意图 → 轮速"；两者都是执行组件，共用同一模板（注入 + tick 外部化 + 参数集中 + PC 桩）——第二个组件落地后，"组件模板"就从纸面变成范本 |
| **收益** | main.c 再瘦 ~50 行；**PID/前馈/解卷绕首次可上 PC 桩**（现在只能上实车凑参数）；标定值具备集中收敛的前提（配合 `car_config`） |
| **风险** | 中。被搬的是**已实车跑通**的控制逻辑，属"实现后搬"，必须台架回归：`M0 60` 稳态、`M0 0` 停车、换向、解卷绕（跨 ±32767/±65536 边界） |

### 9.3 C3 姿态组件（IMU 链，感知栈）

| 项 | 内容 |
|----|------|
| **现状问题** | ① `imu_bridge` 是"胖桥"：~90 行校准状态机 + 漂移补偿 + 滤波调度都在桥里（违反"桥接层只做查 id → 转发"）② `MPU6050` 用**堆 `new`**——直接违反"禁堆 new"铁律（heap 512B）③ 平行数组按 id 索引，`cal_progress` 忽略 id（单例假设 bug） |
| **目标形态** | ① 平行数组 → **通道实例结构体**（device / type / ready / filter / last_tick + 校准状态）② `MPU6050` 改静态池 + placement new ③ 校准 / 补偿 / 调度下沉为**姿态组件**（感知组件，与决策组件同构：只认裸数进出物理量）④ `ImuFilter` 留在 `common` ⑤ `imu_bridge` 回归薄门面 |
| **与 steering 的镜像关系** | `steering` = 执行栈（意图下行）；姿态组件 = 感知栈（裸数上行）。**两项合起来才把"双栈模型"两侧都立起来**，也是"组件模板"能否通用的真正检验 |
| **收益** | 消掉一处禁堆违规；修 `cal_progress` 的 id bug；IMU 链可 PC 桩（用录制的原始 IMU 数据回放测滤波/校准） |
| **风险** | 中。IMU 校准需 ~25s 且只通过 OLED 页 7 观察（串口无上报）→ 改完验证依赖屏幕，建议先补一条"按需上报"命令（`?CAL` 之类）再动 |

### 9.4 与之配套的阶段决策（2026-09-11 用户）

### 9.5 用户口径澄清（2026-09-12）

> "巡线暂时不使用" = **小车先不去跑巡线**；先把**转向、闭环那些做完**。即：先把**执行栈**（转向 + 闭环）做完整，巡线相关（感知拆分、T1 转向模型、`corr → 转向` 融合）整体**后置**。
