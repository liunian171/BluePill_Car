## 一、定位与边界

### 1.1 一句话定位

本 session 属于**工程支持层（工具链/基建）开发**：产出的是"参数怎么来"的能力，不改变"控制怎么跑"的逻辑。类比已有的架构评审、调试总结，同属治理类工作，但本次有可运行的程序产物。

### 1.2 与核心功能开发的边界关系

| 接触点 | 性质 | 处理原则 |
|--------|------|---------|
| pid.c 抗饱和修复（P0-1）、main.c 带符号测速（P0-2） | **必然侵入核心代码**，但都是修地基，且是调节数据可信性的前置 | 按最小侵入原则单列提交，不与工具代码混在一起 |
| 遥测命令、阶跃/继电测试命令 | 核心功能的"调试通道"增量 | 设计目标：可开关、默认关、不进控制路径、不增加控制帧负载 |
| 辨识/整定计算程序 | 纯 PC 端，与固件零耦合 | 放 tools/，版本化帧格式作为唯一接口契约 |
| 标定结果（K/τ/θ、最终 PID 值、前馈系数） | 写回工程配置与文档 | 工具用完即走，参数沉淀才是核心功能的资产 |

边界判据：调参工具链的全部固件改动都应能在"关掉遥测/测试模式"后对原控制行为零影响；达不到即越界。

### 1.3 现状与可推进程度评估

已具备（可直接利用）：在线调参命令（PID/GK/GD/GS）、编码器测速链路（PPR=1466 实测）、串口通道（BT04，可切波特率）、VOFA+ 帧格式实现（firewater_send，未启用）、python 工具目录 tools/、标定常量基本齐全（max_rpm=319）。

缺失（即本 session 工作量）：遥测通道、阶跃/继电测试命令、带符号测速、抗饱和、PC 端辨识与整定程序、操作规范文档。

**结论：可推进程度高。** 硬件链路全部跑通，缺的全是软件增量；遥测 20Hz 约几百 B/s，F103 资源足够；唯一硬瓶颈是 9600bps 带宽（方案：整定期切 115200 或降频）。

## 二、产物构成、用途与适用范围

### 2.1 两层产物

| 层 | 编号 | 产物 | 用途 | 适用范围 |
|----|------|------|------|---------|
| A：本工程 | A1 | 车端固件增量：遥测帧 + 阶跃测试命令 + 带符号测速 + 抗饱和 | 提供可信的三列数据 (t, u, y) | 仅本工程 |
| A | A2 | PC 端辨识+整定程序（python：串口/日志 → FOPDT 辨识 → SIMC 计算 → 参数报告） | 从数据算出 Kp/Ti/前馈 | 本工程直接用，接口通用 |
| A | A3 | 本工程调参操作规范（SOP：安全措施→工作点→录波→辨识→验证→参数回写） | 任何 session/人均可重复执行 | 仅本工程（含巡线环参数扩展） |
| B：通用层 | B1 | 通用 PID 调参方法论规范（数据要求清单、辨识方法选择、离散化换算规则、抗饱和/滤波设计规则、验证指标定义） | 方法论沉淀 | 任何含 PID 的工程 |
| B | B2 | 通用 PC 工具（输入约定为 t/u/y 三列数据，不绑定本工程帧格式） | 辨识+计算+报告生成 | 任何工程 |
| B | B3 | 车端接入手册（最小实现契约：遥测帧格式、阶跃测试最小语义、命名与安全约定） | 复用的接口契约 | 任何工程固件侧 |

### 2.2 受益关系

- **本工程受益**：速度环 PID 整定从试凑变流程；巡线 PD、二期航向环复用同一数据链与流程；调试遥测本身也是后续所有真机调试的基建（补上"无周期上报"缺口）。
- **外部工程受益**（如 A_board Motor 闭环二期、Hexapod、SimpleCar）：B1 方法论照读即用；B2 工具直接吃 t/u/y 数据；B3 告知固件侧最少要实现什么。移植成本被压缩为"实现一份最小车端接口"。
- **分层逻辑**：A 是 B 的第一个实例。B 层从 A 层抽象时只做一次（避免过早设计），抽象的验收标准是"第二个工程能用"。

## 三、关键需求、依赖、风险与决策点

### 3.1 关键需求

| 编号 | 需求 | 说明 |
|------|------|------|
| R1 | 遥测通道带宽与格式 | 9600bps 是硬瓶颈；二进制帧为主，预留文本降级模式；整定期切 115200 |
| R2 | 带符号测速 | 数据可信性前提，不修则辨识结果无意义 |
| R3 | 抗饱和修复 | 闭环/继电数据可信性前提 |
| R4 | 测试安全模式 | 阶跃激励须限幅；提供看门狗；建议整定实验在轮子悬空状态做 |
| R5 | 帧格式版本化 | PC 工具与固件的唯一契约，改动必须升版本号 |

### 3.2 依赖项

D1 P0-1/P0-2 修复（代码，前置）；D2 BT04 波特率切换（硬件配置一次）；D3 标定常量已实测（✔ 已满足）；D4 tools/ python 环境（已有目录）；D5 C2 治理（不阻塞——遥测实现放组装层，不新增 HAL 直调违例）。

### 3.3 潜在风险

| 风险 | 后果 | 缓解 |
|------|------|------|
| 遥测发送阻塞控制帧 | 复活"9600 阻塞 21ms"老坑，数据本身失真 | 发送必须非阻塞（DMA/环形缓冲）或严格限频；遥测点不进 PID 关键段 |
| 阶跃激励过大 | 满占空阶跃电流冲击、跑车 | 限幅参数化 + 轮悬空 + 看门狗 |
| 模型失配被忽略 | 死区/非线性导致"理论最优"实际很差 | 多工作点辨识 + 报告强制输出失真度指标 |
| 通用化过度设计 | B 层提前造框架，无人用 | 只做一次抽象：以 A 层为实例，第二个工程（A_board）验证后才固化 |
| F103 资源超限 | Flash/RAM 挤占核心功能 | 每次改动看链接输出（项目铁律）；遥测缓冲静态分配 |

### 3.4 需预先明确的决策点

1. **遥测形态**：二进制帧（VOFA 兼容，带宽省）为主 + 文本行降级（人眼可读）？——建议：是。
2. **辨识位置**：明确 PC 离线辨识（F103 算力不做在线辨识）。
3. **B 层宿主位置**：先留本工程 tools/ + doc/移植文档/ 下，第二个工程验证后再独立——不建议现在建独立仓库。
4. **阶跃安全模式**：轮悬空为标准实验态；实车阶跃仅允许低速小步长。
5. **遥测默认态**：默认关，命令开启，STOP/急停自动关（防止调试态残留进实车运行）。
6. **工作顺序**：P0 修复 → 遥测 → 测试命令 → PC 工具 → 规范成文。顺序不可换：数据可信性依赖 P0。

## 四、目标描述、优先级与后续方向

### 4.1 Session 目标描述

为本工程建成**"可信调参数据链（车端）+ 辨识整定计算（PC 端）+ 可重复操作流程（文档）"** 三件套，完成速度环 PID 的模型化整定；并将方法论与工具以"第二工程可用"为标准沉淀为通用层。

### 4.2 优先级划分

| 级别 | 内容 | 说明 |
|------|------|------|
| P0（本 session 必做） | ① P0-1/P0-2 修复；② 遥测帧 + 阶跃测试命令；③ PC 辨识脚本最小版；④ A3 操作规范初版 | 三件套最小闭环 |
| P1（本 session 尽量） | ⑤ B1 通用规范成文（从 A3 抽象）；⑥ B3 接入契约初稿；⑦ 遥测 DMA 化 | 通用化抽象 |
| P2（后续 session） | 继电测试命令、参数组 A/B 自动对比、多工作点批量辨识、巡线环整定套用、B2 工具通用化 + 第二工程（A_board）验证 | 扩展与验证 |

### 4.3 后续工作方向建议

- **本工程线**：整定 → 参数回写 car_config/文档 → 巡线 PD 环复用同一数据链（把遥测点扩展到 pos/corr/state）→ 二期航向环（IMU 采样时序届时需重做）。
- **通用层线**：A_board Motor 闭环工程作为第二个实例验证 B1/B2/B3 → 抽取为独立可移植包（届时再考虑独立仓库或 skill 沉淀）。
- **收尾动作**（随 P0 完成）：闭环控制分析报告 §五问题清单勾销 P0 两项；开发跟踪.md 建立条目；本地 commit 注明"调参基建"与"核心修复"分开。
