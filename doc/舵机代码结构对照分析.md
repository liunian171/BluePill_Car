# 舵机代码结构对照分析（框架合规审查）

> 创建: 2026-09-11。定位：**对照《代码风格与模块衔接指南》审查舵机链——哪些符合框架、哪些不符合**。
> 这是 `doc/结构优化顺序分析.md` §8.2 既定顺序的第 1 步（"舵机侧对照分析，用三问拆 main.c 的 sv_lim/servo_apply"）。
> 审查范围：`servo.h` / `servo.cpp` / `servo_protocol.h` / `servo_protocol.cpp` / `servo_bridge.h` / `servo_bridge.cpp` / `main.c` 舵机命令域。
> 依据条款：指南 §1 分层性质、§2 命名注释、§3 机制规则、§4 衔接义务 8 项；评审文档 C1-C8 / D1-D3 / §3.1 组件评估。
> **本文档只做分析，不改代码**（学习思考期约定，实施待立项）。

## 0. 一句话结论

| 层 | 文件 | 评级 | 一句话 |
|----|------|:---:|--------|
| 桥接层 | `servo_bridge.h/.cpp` | ✅ 良 | 静态池 + placement new + id 检查 + 数组化四件套齐全，四桥中最标准；缺 handle 校验与错误通道 |
| 器件层 | `servo_protocol.h/.cpp` | ✅ 良 | 脉宽映射职责单一、注释含量化依据；但头文件把 CubeMX 依赖带进 TU，标定字段裸露 |
| 执行对象层 | `servo.h/.cpp` | ⚠️ 偏差 | **职责清单里写的"限位钳位"实现里没有**；域语义（物理角 0~270）与 main.c（输出域 -115~-65）双轨 |
| 组装层 | `main.c` 舵机命令域 | ⚠️ 错层 | 转向状态机（5 变量 + 2 函数）锁死在 main，本属**执行组件（转向）** |
| 文档形态 | `servo.cpp` 头部 1~172 行 | ⚠️ 严重陈旧 | 大段"待实现"残骸描述不存在的文件与旧架构，与同文件实现（175~199 行）矛盾 |

**核心判断：舵机的"骨架"是四桥里最规范的，问题集中在"肌肉长错位置"——器件翻译对了，但钳位/域换算/标定状态机这三件执行栈的事，一半漏在执行对象层、一半漏在组装层。**

## 2. 不符合框架的部分（按严重度排序）

### S1【高】`servo.cpp` 头部 1~172 行是设计期残骸，与实现互相矛盾

| 项 | 内容 |
|----|------|
| 位置 | `servo.cpp:1-172`（占全文 86%），描述内容为 `servo_core.cpp/.h`、`ServoUART`、`ServoI2C`、PCA9685、`app/main.cpp`、`STM32F4xx_hal_uart.h`、旧命名"功能层/适配层"，并含两段完整"待实现"伪代码 |
| **溯源证据（已核实）** | 本段与**上游驱动工程** `A_board_pwm_driver_test/Core/Src/driver/servo.cpp` 头部**字节级同源**——剥离前两文件全文**仅差 1 行**（上游 `max_angle(180)` → 本仓库 `max_angle(270)`，本项目换 270° 舵机），对应上游 `Servo_Driver_Design.md`。属上游（A 板 / STM32F427 时期）的设计草案随移植整文件复制；文中提到的 5 个文件/类在**上游与本仓库均不存在** |
| 违反 | §2.2 文件头规范（应写：ASCII 分层图 + **本文件在哪一层** + 换平台/换器件动不动这个文件）。现状写了，但写的是**已废弃的架构**，且与同文件 175 行起的真实实现矛盾 |
| 后果 | 新读者/新 Agent 会按头部去改 `servo_core.cpp`（不存在）、去接 `ServoUART`（未实现）；同一文件给出两套分层答案，直接破坏"对号入座选层"的可操作性 |
| 建议 | 删除 1~172 行，改按 §2.2 重写文件头：执行对象层定位 + 依赖白名单（只依赖 `IServoProtocol`）+ "换器件不动本文件"声明 |
| **✅ 处理结果（2026-09-11）** | 1~172 行**原样剥离归档**至 `doc/舵机旧设计稿_归档_上游A板.md`（含溯源说明，只读不维护）；`servo.cpp` 199 → 62 行，文件头按 §2.2 重写（层位图 + 职责 + 依赖白名单 + 可移植性 + 内嵌 S2/S3/S10 偏差标记 + 历史溯源）。Release 编译通过，**Flash 42016B / RAM 4096B 与改动前完全一致**（证实纯注释改动） |

### S2【高】执行对象层职责不完整：声明的"钳位"在实现里不存在

| 项 | 内容 |
|----|------|
| 位置 | `servo.cpp` 头部自述职责含"限位钳位"，但 `Servo::set_angle`（181~185 行）直接 `rate = (angle-min)/(max-min)*1000`，**无任何 clamp** |
| 违反 | §1.2 执行对象层定义明确含"语义翻译：**钳位**/死区/角度→脉宽"；指南 §1 要求"器件级目标"由本层收敛 |
| 后果 | 绕过 bridge 的任何调用（含未来转向组件）传入越界角即输出越界脉宽 → 舵机堵转（安全铁律 §0.2 落空） |
| 建议 | 钳位职责二选一：① 归 servo 内部（`Servo` 自持限位并 clamp，职责自洽）；② 明确归上层转向组件（则须删除头部"钳位"自述）。当前是"两处都声明、两处各做一半"（main.c `servo_set` + `servo_apply` 重复 clamp 两次） |

### S3【高】双坐标域并存且未声明，域换算硬编码在组装层

| 项 | 内容 |
|----|------|
| 位置 | `main.c:147-155` 用**输出域绝对角** [-115, -65]；`Servo` 用**物理角** [0, 270]（`servo.cpp:177`）；换算 `SERVO_RAW_CENTER(135) + a` 硬编码在 `main.c:164` |
| 违反 | 义务 8「单位与坐标域声明：跨模块接口必须在头文件声明单位与坐标域」。`servo.h` / `servo_bridge.h` 均无任何域声明 |
| 后果 | 本项目**已经因此出过事故**（SV -90 被双算成 -180 → 满舵，迫使 §3 修订命令域）。当前隐患仍在：任何新调用方都猜不出 `servo_bridge_set_angle` 吃的是物理角还是输出域角 |
| 建议 | 定域边界（见 §6 待决策）：推荐 **bridge 接口声明为"输出域绝对角"**（对外语义统一、与命令域/文档一致），`+135` 与 clamp 下沉到 servo 内部；届时 `servo_bridge_set_angle(id, -90)` 即直行，语义自明 |

### S4【高】舵机命令域状态机锁死在组装层（评审 C3 在舵机侧的具体表现）

| 项 | 内容 |
|----|------|
| 位置 | `main.c:151-174`：`sv_lim_l` / `sv_lim_r` / `sv_center` / `sv_cmd` / `sv_out` 五个 static + `servo_apply()` / `servo_set()` 两个函数；另散落于 244-246（init/上电回中）、285（二进制 0x10）、312（STOP 回正）、415-436（TXTCMD 分发） |
| 违反 | §1.2 层归属判据：组装层 = "创建实例 + 接线 + 决定谁什么时候跑"；本段做的是**钳位 + 标定限位 + 域换算 + 状态保持**，属**执行组件（运动意图 → 器件级目标）**。同时违反 §2.1（文件级 static 必须 `g_` 前缀） |
| 后果 | ① 无法 PC 桩测试（义务 7 落空）；② T1 转向模型无处可放，只能在 main 继续堆（评审 C3 预判的"膨胀温床"）；③ 标定值（§1.1）与状态耦合在 main，`car_config` 收敛更难 |
| 建议 | 抽 `steering` 执行组件（纯 C，`init(base/limits/center)` + `set(deg)` + `stop()` + 可选 `get()`），状态收进组件单实例；`main.c` 只留"init + 命令转发 + 应答"，即 §4.3 动刀位置 ②③④ |

### S5【中】`SERVO_PROTOCOL_UART` 空壳静默跳过

| 项 | 内容 |
|----|------|
| 位置 | `servo_bridge.h:11` 定义枚举值；`servo_bridge.cpp:21-22` `default: break;` |
| 违反 | 义务 6「非法输入不允许无声 return，至少走一次错误通道」 |
| 后果 | 传 `SERVO_PROTOCOL_UART` 时"初始化成功但什么都没有"——典型静默失败，排查成本高（评审 §3.1 已记"UART 空壳分支") |
| 建议 | 二选一：删除该枚举值（未实现不留接口，符合"预留必须注明启用条件否则删除"），或补实现并在 default 走错误通道 |

### S6【中】`servo_bridge_init` 缺 handle 合法性检查

| 项 | 内容 |
|----|------|
| 位置 | `servo_bridge.cpp:12-24`：查了 `id`，未查 `handle`；`*(PWM_Handle*)handle` 对 `NULL` 解引用 |
| 违反 | 义务 6（init 必须查参数合法性）。对比：`id` 检查做了，`handle` 漏了——同一函数内标准不统一 |
| 后果 | `handle == NULL` 时得到野引用并构造出"看似正常"的对象，故障推迟到首次 set 时爆发，定位困难 |
| 建议 | init 首行统一校验 `id` + `handle`（+ 协议枚举），非法即走错误通道返回 |

### S7【中】桥接层 TU 被 CubeMX 头污染（C6 的连带面）

| 项 | 内容 |
|----|------|
| 位置 | `servo_protocol.h:4` include `pwm.h` → `pwm.h:5` include `tim.h`（CubeMX）。而 `servo_bridge.cpp:2` include `servo_protocol.h` |
| **事实核查（读码确认）** | `pwm.h` **通篇不使用任何 `TIM_` 类型**——`PWM_Handle` 里句柄是 `void *htim`、通道是 `uint32_t channel`，函数指针也全是 `void *htim`（跨平台设计是对的）。它 include `tim.h` 的**唯一原因**是 `TIM_CHANNEL_x` 这类宏，而该宏的**唯一使用者是平台侧文件 `pwm_instance.c`**。即：为一个"实例文件"的需要，把策略层头文件绑架成了 HAL 依赖 |
| 违反 | §1.2 跨平台承诺："为兑现，**头文件也不得 include CubeMX 头**"（C6 已把 pwm.h 记为 ⚠️ 反例） |
| 后果 | ① 换芯片时 `pwm.c` 可零修改，但 `pwm.h` 要动；② **污染扩散**：`servo_protocol.h`（器件层）→ `servo_bridge.cpp`（桥接层）——一个本该"只做 C 门面、与芯片无关"的编译单元里，因此出现了 CubeMX 宏；③ HAL 头携带大量宏与宏函数（`__HAL_TIM_xxx` 等），被包含后换芯片时容易以"编译错误遍地"的形式爆发 |
| 建议 | 🎯 **比"下沉"更简单——直接删除 `pwm.h:5` 即可**（见下方实验）。`TIM_CHANNEL_x` 的真正使用者 `pwm_instance.c` **自己已经 include 了 `tim.h`**（第 10 行），`pwm_platform_ops.c` 也自己 include（第 2 行） |

**实验与实测数据（2026-09-11，读码 + 编译验证）**

| # | 证据 | 数据 |
|:--:|------|------|
| E1 | `TIM_CHANNEL_x` 全仓库真实使用点 | 仅 `pwm_instance.c:16/25/34`（3 处 `.Channel = TIM_CHANNEL_x`）＋ `encoder_platform_ops.c` 用 `TIM_CHANNEL_ALL`（自带 include）＋ `tim.c`（CubeMX 自身）。**`pwm.h` 里一处都没用到**（只有第 132 行注释里出现过名字） |

## 3. 三问拆解：`main.c` 的 `sv_lim` / `servo_apply` 该去哪

> 对应 `结构优化顺序分析.md` §8.2 第 1 步的既定问题。

| 问 | 答 | 判据 |
|----|----|------|
| **① 属于哪一层？** | **执行组件（转向）**，不是组装层 | 它做"运动意图（输出域角）→ 器件级目标（物理角 + clamp）"的语义收敛，无实例创建、无节拍调度。组装层判据是"new/init 别的组件 + 决定谁什么时候跑"，本段两条都不占 |
| **② 实例/状态在哪？** | 5 个文件级 static 标量（`sv_lim_l/r`、`sv_center`、`sv_cmd`、`sv_out`）+ 2 个 static 函数，全在 `main.c`，且**无 `g_` 前缀** | §1.2 执行组件"输入意图与反馈物理量，输出器件级目标"；§2.1 static 命名规则 |
| **③ 与姿态（attitude）是否同构？** | **同构（可共用组件模板），但深度不同** | 同：都是"标定/管线状态长错位置"——姿态的 ~90 行校准+滤波调度在 `imu_bridge`（胖桥），舵机的钳位+域换算在 `main`。异：姿态在**感知栈（上行、多通道）** → 需通道实例结构体 + 数组；舵机在**执行栈（下行、单通道标量）** → 只需单实例结构体，**不需要数组化** |

**由此得出拆分模板（两项共用）**：注入器件接口 + tick 外部化 + 标定量集中 + PC 桩可编译 + 状态归组件实例。
**边界确认（重要）**：`servo_bridge`（桥）与 `PWMServoProtocol`（器件）**不在改造范围**——它们只需按家族契约补错误通道/校验/头文件，不需要搬家。要搬的只有 main.c 里那 7 个符号。

## 4. 钳位该在哪一层（S2 展开）

**结论：钳位不是一个，是两个，分属两层。** 用户提出的判断是对的——**钳位与设置角度是两件事**：
- **限位是配置态**（初始化时设置一次）
- **钳位是执行态的强制约束**（每次必经，且不可绕过）

把钳位写进 `set_angle` 的参数域、或交给调用方自觉执行，都会出错。现状恰好两头都错：限位在调用方（main.c），被调用方（Servo）裸奔。

| # | 钳位类型 | 边界值来源 | 应属层 | 理由 | 当前实现 |
|:--:|---------|-----------|--------|------|---------|
| 1 | **器件物理极限**<br>角度域 → 脉宽域 | 舵机手册：270° 行程 / 500~2500µs | **执行对象层 `Servo`** 管角度域 [0,270]；**器件层 `PWMServoProtocol`** 管脉宽域 [500,2500] | 这是"**器件知识**"，与整车标定无关，换车也必须存在；必须是最底层兜底，任何调用路径都绕不过 | ❌ **缺失**（两层各缺一半，详 R1/R2） |

**当前实现的精确核查（2026-09-11，读码确认，勿凭印象）**

| # | 结论 | 代码依据 |
|:--:|------|---------|
| R1 | `Servo::set_angle` **无任何 clamp** —— 角度超范围会直接算出越界 rate（`uint16_t` 承接，超范围还会截断/回绕） | `servo.cpp`：`rate_0E3 = (angle-min)*1000/(max-min)`，无边界判断 |
| R2 | `PWMServoProtocol::set_position` **无脉宽域兜底** —— `map(rate,0,1000,500,2500)` 对 rate>1000 会**线性外推**出 >2500µs 的脉宽 | `servo_protocol.cpp`：map 后直接 `pwm_set_pulse_us` |
| R3 | 驱动层**有一道兜底，但语义不同、对舵机无效**：`pwm_set_pulse_us` 内 `if (pulse_us > period_us) pulse_us = period_us;` 是"**占空比 ≤ 100%**"的通用兜底（50Hz → 20000µs）。舵机安全域仅 500~2500µs，中间 [2500, 20000]µs 全在"能通过、但已越行程"的危险区；极限情况整周期高电平 → 堵转 | `pwm.c:139-152` |
| R4 | 对比：`pwm_set_duty_0E3` **完全无钳位**（duty 传 2000 → CCR = 2×ARR，硬件表现恒高）。舵机现走 `pulse_us` 路径，此项主要影响电机链 | `pwm.c:121-128` |

> **因此"无兜底"的准确表述**：不是完全没有钳位，而是**现有唯一那道钳位是"通用 PWM 周期上限"，不是"这只舵机的脉宽极限"**——两者相差 8 倍，对舵机起不到保护作用。兜底必须补在**器件层**（`PWMServoProtocol`，因为 500~2500µs 是这只舵机的知识），**不能写进 pwm 驱动**（通用驱动写死舵机参数即破坏其通用性）。
| 2 | **机构行程限位**<br>前轮可用行程 | 实车标定（SS2 手动探边）：输出域 [-115, -65] | **执行组件 `steering`** | 依赖标定值、依赖整车机构几何，属"**车知识**"；应由配置注入（`car_config`），换车只改配置不改代码 | ⚠️ **层错 + 重复**：位置在 main.c（应是执行组件），且 `servo_set` 与 `servo_apply` 各 clamp 一遍 |

**两道钳位的大白话对照（用户理解确认 ✅）**

| | **器件极限**（硬极限 — 保护舵机） | **应用行程**（软限位 — 保护机构） |
|---|---|---|
| 归层 | 执行对象层 `Servo`（角度域）／器件层 `PWMServoProtocol`（脉宽域） | 执行组件 `steering` |
| 数值 | **0~270°** ／ 脉宽 **500~2500µs** | 输出域 **[-115, -65]** ↔ 物理角 **20~70°** ／ 脉宽 **648~1019µs** |
| 性质 | 舵机自身的物理边界，**换车也不变** | 本车转向连杆的可用区间，**标定得来、换车就变** |
| 宽度 | 270°（全行程） | 50°（仅占全行程 18.5%） |
| 定位 | **兜底**——正常路径不应碰到 | 正常路径的**第一道**，实际应用只用这一段 |
| 知识类型 | 器件知识 | 车知识（应进 `car_config`） |

> **两道的关系**：应用行程（50°）比器件极限（270°）窄得多，所以正常路径上先是组件拦；只有当有人**绕过组件**（临时调试代码、未来巡线 corr→转向融合直调 bridge、PC 桩）时，`Servo` 的器件极限才兜底——这才是"纵深防御"的实际含义，也解释了为什么两道都要留。

**为什么"器件极限钳位"归执行对象层（四条判据）**

| # | 判据 | 说明 |
|:--:|------|------|
| 1 | **信息同源** | `Servo` 已持有角度域两端（`min_angle` / `max_angle`），钳位要用的正是这两端 + 它正在做的换算。把钳位搬走 = 同一份信息分居两处 → 必然"各算一半"（现状即如此） |
| 2 | **知识归属是"器件"而非"车"** | 0~270° 是舵机自身物理行程（手册数据），换车 / 换机构 / 改标定都不变 → 属**器件知识** → 归器件侧。同源道理：脉宽 500~2500µs 归器件层 `PWMServoProtocol` |
| 3 | **兜底必须"绕不过"** | `set_angle` 是通往器件的必经入口，在此钳位则任何调用方（`steering` 组件 / 临时调试代码 / 未来 PC 桩）都绕不过。若放 `steering`，只有走组件才受保护；若放 `pwm`，驱动不知道这是舵机（20000µs 对通用 PWM 完全合法），只能给出"周期上限"这类通用边界——正是 R3 那道对舵机无效的兜底 |
| 4 | **层定义本就如此 + 反向检验** | 指南 §1.2 对执行对象层的职责原文即"语义翻译：**钳位** / 死区 / RPM→千分比 / 角度→脉宽"。反向检验：若钳位不在本层，则 `min_angle` / `max_angle` 沦为无意义裸字段（现状），任何人直接经 bridge 调用即失去保护 |

**反过来：机构行程限位为什么不能放这一层** —— `[-115,-65]` 是标定值（**车知识**），`Servo` 不该知道"这台车的转向连杆能到哪"。放进来会导致"换车必须改 `servo.cpp`"，直接破坏"换整车零修改"的跨平台承诺。所以两道钳位边界值不同、语义不同，各归其层，不是重复。

**三条配套设计规则（建议）**

| # | 规则 | 说明 |
|:--:|------|------|
| 1 | **限位与钳位分离** | 限位是配置接口（`servo_set_limit(min,max)` / 转向组件配置），在 init 后设置一次；`set_angle` 只接收目标角，**不在参数里带限位** |
| 2 | **钳位放被调用方，不放调用方** | 钳位必须在被调用方内部强制执行，才能保证"任何路径绕不过"。现状反了：钳位在调用方 main.c,被调用方 Servo 无保护——绕过 bridge 直接调用即失去保护 |
| 3 | **两层各留一道，但语义不同** | 器件极限（层 1）与机构行程（层 2）是**两类**约束，各留一道是纵深防御，**不算重复**；重复指的是"同类约束被放在两处"（评审 §3.1 ① 指的正是这类——`Servo::min/max_angle` 与 main.c 的行程限位是同一类，属真重复） |

> 与 §6 待决策 2 的关系：「限位唯一所有者」指的是**机构行程限位**（同类只留一处）；器件物理极限兜底是**另一类**，不参与"唯一所有者"的选择。
