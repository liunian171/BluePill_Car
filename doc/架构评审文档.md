# BluePill_Car 架构评审文档：耦合性与组件可配置性

> 创建: 2026-09-10（全库源码评审，覆盖 main.c / pwm / motor / servo / encoder / uart / txt_cmd / line_follower / oled / imu_bridge / uart_cmd_parser / CMakeLists）
> 状态标注: 高 / 中 / 低 = 问题严重程度；✅ 优 / ⚠️ 有问题 / ⬜ 待处理
> 关联文档: `AGENTS.md`（规范权威）、`doc/工程文档.md`（架构参考）、`doc/调试总结.md`（§11-§13 近期踩坑）

## 0. 总结论

分层骨架（策略层 / 平台层 / 桥接层 / 协议接口）设计扎实且被文档固化，ops 表 + 依赖注入 + placement new 静态池三种手段贯彻一致。当前主要风险不在驱动层，而在**集成层 main.c 的失控趋势**与**新旧两套命令分发并存**。共 8 项发现（2 高 / 4 中 / 2 低），外加 3 处文档债。

| 维度 | 评级 | 一句话结论 |
|------|:---:|-----------|
| 驱动层解耦（pwm/uart/gpio/encoder/i2c ops） | ✅ 优 | 换平台只需替换 platform_ops 文件，承诺基本兑现 |
| 功能层抽象（Motor/Servo/IMU 协议注入） | ✅ 优 | 换芯片协议只需新写一个 Protocol 类 |
| 解析层 | ⚠️ | txt_cmd 是范本；uart_cmd_parser 是死代码且与 main.c 内联实现双轨并存 |
| 业务层（line_follower / OLED） | ⚠️ | 两处硬件访问逃逸出抽象层，违反自家规范 §5.3 |
| 集成层（main.c） | ⚠️ | 从"组装者"膨胀为"业务容器"，是最该先治理的耦合热点 |

## 1. 模块依赖关系现状

### 1.1 分层依赖全景

| 层 | 组件 | 对下层依赖方式 | 评价 |
|---|---|---|---|
| 应用层 | main.c | 直接引用全部 bridge + HAL 句柄（huart2/hi2c2）+ 中断回调 | ⚠️ 膨胀点 |
| 解析层 | txt_cmd / uart_cmd_parser | txt_cmd 纯逻辑；parser 直调 bridge + HAL（且已死） | 一好一坏 |
| 业务层 | line_follower | **直调 HAL_GPIO_ReadPin**（逃逸抽象） | ⚠️ |
| 业务层 | oled_driver | **直调 HAL_I2C_Mem_Write(&hi2c2)**（逃逸抽象） | ⚠️ |
| 桥接层 | motor/servo/imu/oled_bridge | placement new 静态池 → C++ 对象 → extern "C" 接口 | 模式统一 ✅ |
| 功能层 | Motor / Servo / IMU_base | 持有 IProtocol 接口引用（构造注入） | ✅ 可换协议 |
| 驱动层 | pwm / uart / gpio / encoder / i2c | void* 句柄 + ops 函数指针表 | ✅ 可换平台 |

### 1.2 数据流（控制路径）

| 路径 | 链路 | 状态 |
|------|------|:---:|
| 无线文本命令 | BT04 → USART2 中断 → ringbuf → main.c 主循环 → txt_cmd_parse → main.c switch 分发 → bridge | ✅ 主用 |
| 无线二进制命令 | BT04 → ringbuf → main.c 内联拼帧 → main.c 内联分发 → bridge | ✅ 主用 |
| 旧设计二进制分发 | ringbuf → uart_cmd_parser_tick → uart_cmd_dispatch → bridge | ⬜ **死代码，无人调用** |
| 巡线闭环 | line_follower_update(50ms) → 写 spd_target/spd_dir → main.c PID 环 → motor_bridge | ✅ 主用（仲裁靠约定） |
| 显示/IMU | main.c 100ms 节拍 → imu_bridge / oled_bridge | ✅ 主用 |

## 2. 耦合性发现（8 项）

### C1【高】双套二进制协议实现并存，其中一套是死代码

| 项 | 内容 |
|----|------|
| 位置 | `uart_cmd_parser.c` 全文件（init:108 行 / tick:152 行 / dispatch:209 行）vs `main.c:274-290`（内联拼帧+分发） |
| 问题 | ① main.c 内联了第二套帧解析与分发，uart_cmd_parser 的 init/tick 全工程无人调用，但仍被 CMake GLOB（`CMakeLists.txt:46-51`）编译并烧进 Flash；② 两套语义已分叉：parser 版的 CMD_MOTOR_SET_RPM 不做接管权退出（无 line_follower_enable(0)）、无 0 速必停语义，响应也不写 OLED 应答页；③ 响应格式不同（parser 发二进制 STATUS 帧，main 发文本 ack） |
| 影响 | 改协议可能改错文件；死代码白白消耗 64KB Flash 里的空间；uart_cmd_parser.h 头文件的"典型调用流程"注释会诱导下一个人把它接回去，接回去即复现调试总结 §12 的"车复活"事故 |
| 建议 | 二选一：**A（推荐）** 收编——把 main.c 内联分发迁入 parser（带回接管权语义与文本 ack），main.c 只留 tick 调用；**B** 删除 parser + 头文件，main.c 内联版扶正为唯一实现。另需注意：二进制命令目前不做 `pid_reset`+`brake` 的 0 速语义路径与文本 M0 0 完全对齐（main.c:282 直接写 spd_target，靠 50ms 环的 `<1.0f` 分支兜底），收编时统一 |

### C2【高】line_follower 直调 HAL，核心业务逻辑不可测

| 项 | 内容 |
|----|------|
| 位置 | `line_follower.c:245-249`（5 路 `HAL_GPIO_ReadPin(OUTx...)`），`line_follower.c:17`（include main.h） |
| 问题 | 巡线状态机（全库最核心的业务逻辑）直接读硬件；AGENTS.md §5.3 第 1 条明文规定"算法/状态机/协议层禁止直调 HAL"，且在文档中已将此处列为反例，但代码未改 |
| 影响 | PC 测试桩无法编译 line_follower（目前唯一能上 PC 测的只有 txt_cmd）；换传感器（如 I2C 灰度、模拟比较器）必须改状态机内部 |
| 建议 | 注入传感器读接口：一行函数指针 `uint8_t (*read_sensors)(uint8_t idx, void *ctx)` 或 `line_follower_sensors_ops` 表，main.c 初始化时绑定 HAL 实现，PC 桩绑定模拟实现。改动面小（一个 getter + 五处调用点），收益最大 |

### C3【中】main.c 上帝模块：组件逻辑锁死在集成层

| 项 | 内容 |
|----|------|
| 位置 | `main.c` 全文件（600 行）：ISR 回调（95-100）、应答格式化 ack/tx_raw（103-131）、**舵机命令域状态机**（sv_lim/sv_center/sv_cmd/servo_apply，141-174）、**PID 速度环 + 前馈 + 编码器解卷绕**（456-505）、OLED 组版（509-573）、VOFA+ 协议（72-92） |
| 问题 | 舵机命令域（clamp/限位/回正语义）和速度环（PID+前馈+解卷绕）是独立的可复用组件，却以 static 变量形态锁死在 main.c；巡线融合（T4）后 main 还会继续膨胀 |
| 影响 | 转向模型（T1）只能在 main.c 里继续堆；两套逻辑无法上 PC 测试桩；任何新功能都往 main 加，回归风险集中 |
| 建议 | ① 抽 `steering` 组件（纯 C，sv_lim/sv_center/servo_apply + clamp 进去，SV/SL/SR/SC 命令只做转发）；② 抽 `speed_loop` 组件（PID 环 + 前馈 + 解卷绕，输入 enc/target，输出 motor_bridge 调用）；③ 两者都按 txt_cmd 模式建 PC 测试桩 |

### C4【中】控制权仲裁靠人肉约定，安全语义依赖记忆

| 项 | 内容 |
|----|------|
| 位置 | `main.c:282/283/284/319/328/337` —— 6 处手动命令各自调用 `line_follower_enable(0)` |
| 问题 | spd_target/spd_dir 是共享全局，巡线与手动命令的仲裁机制 = "每条新命令都要记得退巡线"；STOP 的 kill switch 语义靠 3 行顺序调用（307-312）维持 |
| 影响 | 新增一条命令漏写 `line_follower_enable(0)`，即复现调试总结 §12"急停后车复活"实车事故——这是安全问题不是风格问题 |
| 建议 | 集中仲裁：在 main 或独立模块维护 `manual_override_tick`，任何手动指令更新它；`line_follower_update` 入口检查"距上次手动指令 < N ms 则不写 target"（或直接由仲裁函数决定 target 来源）。把"6 处散落调用"收敛为"1 处机制" |

### C5【中】OLED 硬编码 I2C 句柄，同库两套 I2C 访问模式

| 项 | 内容 |
|----|------|
| 位置 | `oled_driver.cpp:17`（include i2c.h）、`oled_driver.cpp:22`（`HAL_I2C_Mem_Write(&hi2c2,...)`） |
| 问题 | IMU 走 `I2C_Handle` + ops（i2c_hardware_ops.c 封装），OLED 直接抓全局 hi2c2——同一代码库存在两种 I2C 访问抽象，违反"平台依赖全部收敛到 *_platform_ops.c"（AGENTS §4.1） |
| 影响 | OLED 换 I2C 实例 / 软件模拟 I2C / 换平台都要改驱动内部；历史踩坑 §1（&hi2c2 解引用硬错误）的根源模式仍存活 |
| 建议 | oled_bridge_init 增加参数传入 `I2C_Handle*`（复用 i2c_hardware_ops），oled_driver 内部只经 ops 写寄存器。改动小（一个 init 签名 + 内部发送函数） |

### C6【低】pwm.h 策略头拖入 CubeMX 依赖

| 项 | 内容 |
|----|------|
| 位置 | `pwm.h:5`（include tim.h） |
| 问题 | 策略层头文件 include CubeMX 生成的 tim.h；但 PWM_Handle 内部用 void*，该 include 仅为 `pwm_instance.c` 里的 TIM_CHANNEL_x 常量服务 |
| 影响 | 所有 pwm.h 的使用链（motor_protocol.h → servo_protocol.h → main.c）被动依赖 CubeMX 头；"换平台 pwm.c 零修改"承诺打折（头文件也算） |
| 建议 | tim.h include 下沉到 `pwm_instance.c` 与 `pwm_platform_ops.c`（它们本来就是平台文件），pwm.h 只留 stdint |

### C7【低】电机桥接层混入硬件布线差异 + 越界检查不一致

| 项 | 内容 |
|----|------|
| 位置 | `motor_bridge.cpp:27,34`（`if (id == 1) rpm = -rpm`）；`motor_bridge_init`（11-22 行，无 id 越界检查）vs `servo_bridge_init:14`（有 `id >= MAX_SERVOS` 检查） |
| 问题 | ① E2 编码器/电机接反的硬件差异硬编码在通用桥接层，换车/换接线要改桥接代码；② MAX_MOTORS=8 的静态池，init 传 id≥8 直接越界写静态池外的内存（比 servo 更危险，因为 init 没有 nullptr 兜底） |
| 影响 | 可移植性小损；一个潜在越界写（当前调用点固定 0/1，风险未触发） |
| 建议 | init 加 `if (id >= MAX_MOTORS) return;`；方向取反上提为 init 参数 `int8_t dir_invert`（或 config 表字段），桥接层回归纯转发 |

### C8【低】handle_to_id 地址差映射的隐式脆弱性

| 项 | 内容 |
|----|------|
| 位置 | `uart_cmd_parser.c:110` + `common/tool.h`（handle_to_id） |
| 问题 | 用 `(目标地址 - 基准地址) / sizeof(type)` 把 HAL 句柄映射为数组下标，隐式依赖"各 UART 句柄在 .bss 段连续排列"这一未承诺的链接器行为 |
| 影响 | 当前仅死代码使用（C1）；若启用，链接顺序/编译器变化可能静默错位 |
| 建议 | 随 C1 一并处理：启用 parser 时改为显式注册表（init 时登记 huart 指针 → 遍历比对），O(4) 代价换确定性 |

## 3. 组件可配置性评估

### 3.1 逐组件评估

| 组件 | 可配置项 | 评级 | 问题与建议 |
|------|---------|:---:|-----------|
| txt_cmd | 命令集编译期固定；纯逻辑、零 HAL、PC 桩 41 用例 | ✅ 优 | **文档债 D1**：头注释"居中域： 0=直行"与实现/设计文档 §3 的"输出域绝对角"矛盾（见 3.2） |

## 4. 整体优势与不足

### 4.1 优势（应保持的做法）

1. **四层模型真实落地**：策略/平台/桥接/协议接口不是纸面架构——pwm/uart/gpio/encoder/i2c 五套 ops 表、Motor/Servo/IMU 三个协议注入点全部可验证替换
2. **内存安全模式统一**：placement new + 静态池在 motor/servo/imu 桥接层一致执行，堆分配禁令有踩坑记录支撑（调试总结 §5）
3. **txt_cmd 范本效应**：踩坑（§11 scanf 静默失败）→ 纯逻辑模块 → PC 测试桩 41 用例，是"事故转化为架构改进"的完整闭环，应作为后续新模块（steering/speed_loop）的模板
4. **文档回写机制**：调试总结/开发跟踪/设计文档三层联动，决策可追溯（如舵机命令域修订原因记录在设计文档 §3）

### 4.2 不足（按治理优先级）

1. **集成层失控**（C3）：main.c 从组装者变成业务容器，舵机命令域与速度环最该先拆出
2. **协议双轨**（C1）：新旧两套二进制分发并存且语义分叉，是一致性最大风险
3. **规范选择性遵守**（C2/C5）：§5.3 测试友好铁律写了，line_follower 与 OLED 两处未执行
4. **仲裁靠约定**（C4）：安全语义（STOP 不可复活）依赖每处调用点的自觉，缺机制保障
5. **配置散落**（3.3）：标定常量无常量表，标定知识靠翻代码

### 4.3 建议执行顺序（与开发路线对齐）

| 序 | 动作 | 对应发现 | 理由 |
|:---:|------|:---:|------|
| 1 | 删除或收编 uart_cmd_parser | C1 | 纯减法/一致性，无功能风险，顺带清 Flash |
| 2 | line_follower 传感器注入 | C2 | T4 巡线融合的前置——融合逻辑要能上 PC 桩 |
| 3 | 抽 steering 组件（含限位归一 + D1 注释修正） | C3 | T1 转向模型正好需要该组件做地基 |
| 4 | 接管权仲裁集中化 | C4 | 与 3 同批，避免新组件继续沿用散落 enable(0) |
| 5 | OLED I2C 注入 | C5 | 独立小改动，穿插 |
| 6 | car_config.h 收敛标定量 | 3.3 | 穿插；配合参数持久化（T5）一起做收益最大 |
| 7 | 其余低级别项（C6/C7/C8/D2/D3） | — | 随相邻改动顺手处理 |
