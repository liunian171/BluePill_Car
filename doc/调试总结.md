## 技术要点

### 1. I2C 硬件 ops 桥接

IMU 驱动通过 `I2C_Handle` + ops 表访问 I2C，但 HAL 提供的是 `I2C_HandleTypeDef`。

```
IMU 驱动期望: I2C_Handle { .i2c_context, .ops }
HAL 提供:      I2C_HandleTypeDef hi2c2
```

**解决**：编写 `i2c_hardware_ops.c`，将 `HAL_I2C_Mem_Write/Read` 阻塞调用封装为 ops 表中的 `start_transfer`，并在完成后同步调用回调。IMU 驱动完全无需感知底层用的是硬件 I2C 还是软件模拟。

### 2. STM32 浮点 printf 支持

`--specs=nano.specs` 默认不包含 `%f` 格式输出。两种解法对比：

| 方案 | FLASH 增加 | 说明 |
|------|-----------|------|
| `-Wl,-u,_printf_float` | +10KB | 直接启用，简单粗暴 |
| 整数拆分 `%d.%d` | 0 | 用 `(int)val` 和 `(int)\|((val - (int)val)*10)\|` 替代 |

该项目 FLASH 仅 64KB，选择第二种。

### 3. 互补滤波调优

| 参数 | 改前 | 改后 | 效果 |
|------|------|------|------|
| 初始校准采样 | 30 次 (15秒) | 100 次 (25秒) | 零偏估计更准 |
| α (加速度信任度) | 0.10 固定 | 0.02~0.50 动态切换 | 静止时靠 accel 拉回，运动时靠 gyro 积分 |
| 陀螺零偏补偿 | 启动时一次 | 运行时持续跟踪 | 温度漂移自动补偿 |
| 加速度模值检测 | 无 | 判断静止/运动 | 动态切换 α |

### 4. 嵌入式 C++ 内存安全

`new` 在裸机环境中依赖 heap，STM32 默认 heap 仅 0x200（512 字节），分配失败返回 NULL 却不抛异常（`-fno-exceptions`），后续解引用直接硬错误。

**placement new**（定位 new）代替堆分配：

```cpp
static uint8_t g_pool_mem[MAX][sizeof(Object)];  // 编译时分配，零堆
new (g_pool_mem[id]) Object(args);               // 在预分配内存上构造
```

### 5. UART 接收方案

| 方案 | 是否丢字节 | CPU 开销 | 适用场景 |
|------|-----------|---------|---------|
| 轮询 `HAL_UART_Receive` | ❌ 多发并发时丢 | 高（忙等） | 调试用 |
| 中断 + ringbuf | ✅ 不丢 | 极低 | 产品级 |

**推荐模式**：ISR 中只做 `ringbuf_write` + 重新使能接收，主循环中解析 ringbuf，不在中断里做任何业务逻辑。

### 6. 串口二进制协议

```
PC → STM32:  0xAA | cmd | [id] | [参数...] | 0xFF | 0xFF
STM32 → PC:  0xAA | cmd | id  | status    | 0xFF | 0xFF
STM32 → PC:  M0:128RPM\r\n (文本回应，调试用)
```

- float 参数使用小端序 IEEE 754
- 帧尾两字节 0xFF 0xFF 降低数据中偶然匹配概率
- 帧长度：5B（无参）~ 9B（含 float）

### 7. GPIO 掩码与编号混淆

`UserGPIO_Handle.gpio_pin` 存储的是 GPIO 位掩码（如 `GPIO_PIN_13 = 0x2000`），但平台函数 `usergpio_stm32_write` 里又做了一次 `1 << gpio_pin`，导致 `1 << 0x2000` 溢出为 0，引脚永远写不进去。

**解决**：`gpio_pin` 直接传给 `HAL_GPIO_WritePin`（它本身也期望掩码），删除多余的移位。

### 8. TIM 时钟频率计算

STM32F103 定时器时钟规则：
- APB1 预分频 ≠ 1 → TIM 时钟 = PCLK × 2（APB1=36MHz → TIM2/3/4=72MHz）
- APB2 预分频 = 1 → TIM 时钟 = PCLK（不分频，APB2=72MHz → TIM1=72MHz）

原代码对 APB2 定时器直接 `PCLK2 × 2` 算出 144MHz，导致 PSC 计算偏大，频率偏低。

**解决**：用 `PCLK2 < HCLK` 判断 APB2 是否有分频，有分频才 ×2。

### 9. 命令响应延迟分析

用户实测单电机命令延迟 ~2.5秒，双电机同时发时 M1 比 M0 再晚 ~2.6秒。

**原因**：
1. 每 250ms 显示刷新中 I2C 超时 100ms，串口字节在这期间堆积
2. 原代码每次主循环只处理 1 个 ringbuf 字节，9 字节的帧要 9 轮循环
3. M0 和 M1 的帧之间夹着显示刷新，M1 的剩余字节排队等了 ~5 秒

**解决**：
- I2C 超时 100ms → 10ms
- `while(ringbuf_read(...))` 一次性清空 ringbuf

### 10. max_rpm 实测标定

实测数据（128 RPM 指令，64% 占空比）：

```
每秒编码器计数 ≈ 4980 counts/s
实际转速 = 4980 / 1466(PPR) × 60 = 204 RPM
实际 max_rpm = 204 / 0.64 = 319 RPM (原设定 200)
```

修正后 `motor_bridge_init` 的 `max_rpm` 从 200 → 319。

## 11. 无线命令 `M0 60` 无响应（2026-09-09）

| 项 | 内容 |
|----|------|
| 现象 | BT04 无线链路 `PING`/`STOP`/`B0`/`B1` 均正常应答；`M0 60`/`M1 60` 无任何应答，OLED 页6 也不更新 |
| 根因 | **newlib-nano (nano.specs) 下 `sscanf "%f"` 需要 `-u _scanf_float` 否则静默失败**（与 §2 的 `%f` printf 同类坑）。所有依赖 sscanf 浮点解析的命令（M0/M1/GK/GD/GS）解析返回 0 被静默丢弃；strcmp 类（PING/STOP）和整数 sscanf 类（P/GC/GT）不受影响。附带发现：`ack("GK:%.1f")`、`cmd_note("%.0f")` 同缺 `_printf_float`，显示也是坏的 |
| 解决 | ① 文本命令解析抽成纯逻辑模块 `driver/txt_cmd.c`（手写 float/int 解析，不用 scanf %f）；② printf 浮点显示全部改为整数拆分 `%d.%d`（dec1 辅助函数）；③ 解析模块按 AGENTS.md §5.3 建 PC 测试桩（`test/host_txt_cmd_test.c`，41 用例），测试桩当场抓到并修复"小数位丢失"与"6.0.5 误接受"两个解析 bug 后全过 |
| 证据 | PC 测试桩 41/41 PASS；Release 编译 FLASH 40452B(61.72%，较 sscanf 版省 2.3KB)；**真机回归通过（2026-09-09）**：`M0/M1 60` 应答正常、0 速停车、GK/GS 在线调参生效 |
| 教训 | **newlib-nano 的 printf/scanf 浮点支持双双默认缺失**——凡遇"带小数参数的命令无响应/浮点显示为空"先查这里。规避：数值解析手写或整数化，显示用 `%d.%d` 拆分 |

## 12. STOP 后车"复活" + 手动 M0 60 无轮子响应（2026-09-09 实车）

| 项 | 内容 |
|----|------|
| 现象 | ① `STOP` 应答正常且立即急停，但过一会车轮自行恢复转速，**先右轮后左轮**；② `M0 60`/`M1 60` 应答和 OLED 都正常，轮子不转 |
| 根因 | **巡线使能态残留**（台架 `--auto` 测试末尾发过 `L 1`，同一次上电未断电则状态保留）。① 巡线状态机每 50ms 重写 `spd_target`，STOP 清零后立即被覆盖——车离线进入 SEARCH 态每 800ms 换向扫描，与"先右后左恢复"完全吻合；② 手动目标同样每 50ms 被覆盖成 SEARCH 的小差速目标（≈24/36 RPM），表现为"无响应" |
| 解决 | **接管权语义**：① `STOP` 升级为彻底急停——同步 `line_follower_enable(0)` + `set_auto(0)`（关自动启动防重启复活），应答变 `STOP OK LINE OFF`；② 所有手动电机指令（文本 M0/M1/B0/B1 + 二进制 0x01/0x02/0x03）执行时自动 `line_follower_enable(0)` 退出巡线接管 |
| 证据 | 实车现象与 SEARCH 扫描周期（右→左 800ms 交替）吻合；PC 测试桩回归不受影响（只动执行层不动解析层）；**实车复测通过（2026-09-09 W6）**：STOP 不再复活（`STOP OK LINE OFF`）、L 1/0、M0/M1 30 全过 |
| 教训 | **控制权冲突**：多路来源写同一目标变量时，必须定义"谁有接管权"——急停/手动指令必须压过自动状态机，否则状态残留会让指令"看起来执行了但被覆盖"。语义上：STOP = kill switch，必须不可被自动逻辑复活 |

## 14. 蓝牙命令延迟"比以前高"的定量定位（2026-09-11 真机）

| 项 | 内容 |
|----|------|
| 现象 | 用户反馈：蓝牙串口发指令后小车反应延迟比之前高一些（背景：刚烧录 steering 批次固件，需排除"是否本次改动引入"） |
| 测量方法 | PC 端 `COM15`（BT04 SPP）/ 9600-8N1，**1ms 轮询**测"命令写入 → 首字节到达"；每命令 20 次；对照巡线开/关、steering 路径 vs 非 steering 路径、命令长度 |
| 实测数据 | `PING`(6B) p50 **31.8**；`SV -90`(8B，走 steering) p50 **47.5**；`M0 60`(6B) p50 **61.7**；`GS 30`(7B) p50 **47.1**；`S`(2B) p50 **63.5** ms。**全部样本落在 ≈31 / 47 / 62 / 78 / 109 ms——量化到 ≈15.5ms 网格**（2/3/4/5/7 倍） |
| 根因 | **BT04 蓝牙模块的固定节拍（≈15.5ms 打包/投递粒度）主导，固件不是瓶颈**。四条证据：① 延迟与命令类型无关（走不走 steering 同分布）；② 与命令长度无关（2 字节的 `S` 反而偏慢）；③ 延迟**离散量化**为固定网格（外部定时器特征，非软件抖动）；④ **连发 10 条 `PING`，10 个应答在同一时刻批量到达**（间隔 0ms）= 模块缓冲后批量投递；⑤ 固件空闲流量 0 字节，主循环处理 <1ms |
| 结论 | **本次 steering 批次改动未引入延迟**（steering 路径 47.5ms 与 M0 61.7 / PING 31.8 同分布、同量级）。用户感知的"变高"更可能来自蓝牙链路环境（干扰 / 距离 / 模块状态）或发送端（手机 APP 侧处理与渲染）。建议同链路分别用 PC 脚本与手机 APP 复测对比 |
| 固件侧可控项（**未做**，供后续选做） | ① `ack()` 是**阻塞发送**（`HAL_UART_Transmit`，9600 下 6~11 字节 = 6~11ms）——影响"应答完成时刻"而非首字节；② 100ms 周期内 **OLED 8 页连续 I2C 事务**，命令若落在刷屏窗口需等待（最长约 20ms）→ 优化方向：UART 改**中断/DMA + 发送环形队列**，OLED 改**分页轮转**（每周期只刷 1~2 页） |
| 教训 | 延迟问题先**量化再归因**：区分"首字节延迟"与"完整应答时间"、看延迟是否**量化**（网格=外部节拍）与是否随命令内容变化（量化点内 = 与软件无关），比凭体感判断改动影响可靠得多 |

## 13. 舵机微步推不动：0E3 占空比量化（2026-09-09）

| 项 | 内容 |
|----|------|
| 现象 | SS1 实测占空比验证中位/限幅全部正确（7.50%/7.79%），但 `SV+`（±1°）推不动舵机 |
| 根因 | **0E3 千分比占空比接口在 50Hz 下量化步长 = 20ms/1000 = 20µs**，对 270° 舵机即 **2.7°/步**——±1° 指令小于一个量化步，被截断。硬件 ARR=19999（1µs/格）本来够细，瓶颈纯在软件接口 |
| 解决 | pwm 策略层新增 `pwm_set_pulse_us()`（脉宽直写 CCR，`CCR = pulse_us×(ARR+1)/周期µs`，50Hz 时 1µs 分辨率）；`PWMServoProtocol::set_position` 改用它。角度→rate 仍走千分比（量化 0.27°，够用） |
| 证据 | 实测占空比与理论吻合反推量化步长；**烧录后实测**：SV 7/8/9 → 7.75/7.79/7.83%，SV+ 每步 ~1° 可见 |
| 教训 | **接口精度要匹配用例**：千分比占空比对电机（20kHz, 每步 50µs 周期占空比）够用，对舵机脉宽控制（50Hz）差一个量级；同类抽象接口换场景时先算一遍量化误差 |

## 15. newlib-nano 的 printf 不支持 %llu（2026-09-12，发现于 BluePill_Exam）

| 项 | 内容 |
|----|------|
| 现象 | 计算器结果显示严重异常：`80.00` 打印成 `lu.0lu`，`-6.00` 打印成 `-lu.0lu`；PC 测试桩 27/27 全过（纯逻辑无 printf），上真机才炸——又是"PC 过、真机挂"形态 |
| 根因 | **nano.specs 的 nano-printf 默认不支持 long long**（`%llu`/`%lld` 格式串被按短处理，输出字面量碎片）。与 §2 的 `%f`、§11 的 `%f` scanf 同族——newlib-nano 对"宽格式"的裁剪是系统性的：浮点 printf/scanf、long long printf 默认全缺 |
| 解决 | 结果值先用 unsigned long（32 位）拆分：整数部分 `(unsigned long)a`，小数部分 `(unsigned long)((a-ip)*100+0.5)`，进位单独处理（fp≥100 → ip+1, fp-=100），格式串只用 `%lu.%02lu`。溢出在逻辑层先行拦截（\|v\|<1e8），保证 32 位拆分不越界 |
| 教训 | **newlib-nano 格式支持三坑合一条目**：凡 printf/scanf 输出"莫名其妙少一截/出字面碎片"，按 ① `%f` 缺 → ② `%llu` 缺 → ③ scanf `%f` 静默失败 顺序排查。规避通则：显示一律整数拆分 `%d.%d`（32 位以内），格式串里不出现浮点与 long long；PC 桩无法覆盖 printf 行为，格式相关代码必须上真机冒烟 |

| 解决 | ① **硬件即效**：OLED 排线插稳（用户实测"动排线即黑屏"= 触发条件）→ ODOM 立即回 20Hz。② **固件根治（2026-09-19 已实施）**：`OLED_IO_TIMEOUT_MS` 100→**20ms**（正常 128B@100kHz ≈11.7ms，留余量）+ `oled_driver.cpp` **连续失败熔断**（连续 6 笔失败 → 冷却跳 60 笔 ≈3s 零 I2C 阻塞 → 到期自动试探）+ **失败可见**（`tx_fail_count()/fused()` 经 `oled_bridge` 上 OLED 页 7，异常态显 `E<失败数> O<溢出数> FZ`）。③ 顺带把同族"沉默失败"补齐：`RINGBUF_SIZE` 128→**240**（容量 239B）+ 溢出计数（`ringbuf_overflow`，饱和 255）+ PC 桩 `host_ringbuf_test` **16/16** |
| 编译证据 | Release 零新增告警（仅剩 2 处历史 `-Wformat-truncation`）；**Flash 62440B(95.28%) / RAM 11832B(57.77%)**（+224B Flash / +232B RAM —— 扩容 ringbuf 的固定开销） |
| **真机复验（2026-09-19 拔插 USB 后，COM17）** | ① `ODOM 1` → 0x51 **205 帧/10s、ts 全 50ms = 20.00Hz**（修复前 10.00Hz）✅；② ATT 0x52 = 102 帧（10Hz）✅；③ ITEL 间隔 200ms、IMU 有数（陀螺 -29,19,-15 / 欧拉 -40,-71,6）✅；④ 突发 **30 条→30 零丢**（修复前 28）、**40 条→40 零丢**（修复前 24）✅；⑤ 突发 60 条（300B）→ 53，仍丢 7 —— **300B > 239B 容量，属容量上限的预期行为**（且现在经页 7 `O<n>` 可见），非本次缺陷 |
| 教训 | ① **排除法要看"恢复后是否好转"，不看"移除后是否照旧"**——对"异常即代价"型缺陷，移除器件同样制造异常（本案拔 OLED 与半断电等价），据此排除会一路错到底；② 有阻塞超时的外设（OLED 100ms）与电机控制环同住在一条主循环里 = 架构级隐患，"每轮重试 + 块首重置节拍门"会把单次故障放大成**持续**故障；③ 定位主循环节拍，首选**设备侧证据**（机内记录 tick / 遥测帧内 ts），主机侧观测会被 USB/OS 缓冲欺骗；④ 复现优先级：先"原地复测"（板子在线时测量成本≈0）再考虑拆装，本轮所有测量均未动一根线 |

## 25. Flash 瘦身批次：95.28% → 72.62%（2026-09-19）✅

| 项 | 内容 |

| 背景（=验证内容） | P2 落地后 Flash 冲到 **62440B / 95.28%**（64KB 上限），任何新功能前必须先瘦身。用户口径："先瘦身吧" |

| **改动与收益（逐项实测）** | ① **紧凑 sinf/cosf**（新增 `common/math_fast.c`，fdlibm 二段规约 + 四次多项式）→ **−4424B**：原实现只为全范围精度链入 `__kernel_rem_pio2f`(1904) + `two_over_pi`(792) + `__ieee754_rem_pio2f`(732) + kernels(636)，而本车调用域 ≤2π；② **删 I2C2 事件中断**（`it.c` 不再调用 `HAL_I2C_EV_IRQHandler` + `i2c.c` 的 USER CODE 区关 NVIC）→ **−2920B**（hal_i2c 5313→2361）；③ 删 8×16 字库 + `show_string/show_chinese`（死代码）→ **±0B**（该段**早已被 --gc-sections 自动剔除**，删除属代码卫生）；④ **Release 启用 LTO**（`-flto` 编译+链接）→ **−7496B** |

| 教训 | ① **瘦身先分析再动手**：本轮真正的浪费是"为通用精度付出的库代码"（三角规约链 4.1KB）与"生成代码默认打开却无人使用的功能"（I2C 事件中断），而不是"我们的业务代码写得肥"；② **map 统计必须排除 Discarded 段**，否则结论完全跑偏（差点去优化一个已经很小的大头）；③ "删文件"未必省 Flash —— 已被 `--gc-sections` 剔死代码（8×16 字库）时收益为 0，**删前先用 nm/map 确认该符号是否真在固件里**；④ **LTO 收益最大却折戟**：−7.5KB 诱人，但真机 HardFault → **"编译过 + 体积小" 不等于可用**，凡是全局优化（LTO）必须过真机判活这一关（本案用 SWD 读 `uwTick` + `HFSR/CFSR` 定位，5 分钟给出结论）；⑤ 生成代码里的"默认开启项"（NVIC/中断/字库/大字号接口）是嵌入式项目最容易被忽视的常驻成本 |
